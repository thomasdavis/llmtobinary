Legend: **verified** = automated tests in this repo pass · **live** = exercised on deployed Cloudflare Workers · **not yet** = not implemented or not exercised.

- **live** Real OpenAI (`gpt-5.4-mini-2026-03-17`, low reasoning) on staging: the model's first two drafts were malformed (184/188 bytes), `check_candidate` diagnostics led it to a valid 192-byte submission; in a second, browser-driven run the loop ended **passed** in 16 s and the generated bytes (sha256 `1ef49da0…f069`) executed locally in the browser printing `146`.

Evaluate any smoke output with `tools/research-cli/src/eval-smoke.ts`.

## Generation feedback and custom prompts
- **live** check_candidate is task-aware: the loop passes the entry signature and the effects the task's tests compare. A wrong signature (ANMA-K-003), or a program that never calls display.present / a terminal import when those are tested (ANMA-K-002), fails the static check, so no submission is spent. This came from a live gpt-6-luna ball/paddle session whose program never drew.
- **live** A program with no framebuffer gets "the program never draws" instead of two framebuffer hashes.
- **live** "Write your own" prompt mode, with an input editor (up to 8 u64/bool), a return type, the devices it may use, a draft kept in localStorage, and "Edit as my own prompt" to start from a curated task. Verified live on staging: a digit-sum prompt generated a program that returns 29 for 9875.

- **live** Programs that run until input ends them (or forever): a model example that claims no result/terminal text holds while the program waits for input (examples run with no ticks). A claimed result is reported as "never returned" with that reason, and open-task prompts that permit input say so. Found live: a visitor's "snake runs forever" prompt failed K-005 "did not finish", then stalled. Rerun on staging, it succeeds.
- **live** Loop robustness: the server's `attempt.error` gets a real, stored sequence number (the browser dropped it before). When a stream ends early, the browser follows the attempt on the server until it finishes and shows the server's error text. The workerd Durable Object suite could not start under host load (pool startup timeout), so it has not been rerun for this change.

- **live** Drawing without presenting:
  - ANMA-W-004 (advisory) is raised when a program calls display.clear/pixel but never display.present.
  - In the generation loop this is an error for every task, open ones included.
  - The manual (prompt v3) says drawing goes to a hidden buffer until present.
  - The framebuffer panel says when nothing has been presented.
  - Found live: a model's "snake" drew 48 pixels a tick and never presented, so the screen stayed empty.

- **live** Limits for complex programs (PRD 7.x/14.1):
  - Loop budget: 100 turns, 64 checks, 16 submissions, 100k output tokens per turn, 2M per session, 60 min.
  - Context and sizes: 2M-character context with older drafts elided first; candidates up to 192 KiB; response text 1 MiB; annotations 1 MiB.
  - Fuel: unbounded for visitor-started runs; open-task examples get 20M instructions.
  - Server and prompts: open tasks use `high` reasoning and a no-placeholder instruction; prompts up to 16,000 characters; recovery TTL 2 h; Worker `cpu_ms` 300,000.
  - Storage: the Durable Object stores the conversation in chunks under the 2 MiB value limit and writes candidates once.
- **live** Lost-attempt recovery: a fresh Durable Object that finds an attempt persisted as running marks it lost, answers any dangling tool call, and stores an `attempt_lost` event; the browser resumes up to twice. Unit-tested; a live redeploy-mid-attempt probe finished before the restart, so the live path is not yet exercised.
- **open** Root cause of attempts that end silently mid-session: seen twice on long custom prompts (turn 6, around 33k output tokens, 262 s). Needs Worker logs from a failing run.

- **live** Session debug archive: every session is archived to R2 (`llmtobinary-debug`, `-staging`) after each attempt, on lost-attempt recovery, and before purge. **Share for debugging** adds the browser record and yields `llmtobinary debug <env> <id>`; `scripts/debug-session.mjs` fetches and summarizes it. The consent text discloses the archive. Verified live on staging.

## First-visit experience (simple view)
- **live** An explainer opens on a first visit (native `<dialog>`; ✕, Esc or backdrop closes it; remembered; reopened with "What is this?").
  - It has 6 steps: binary and compilers, the AI-writes-binary idea, why ANMA-1 (registers vs named values), a colour-coded 16-byte instruction, why it would need to be manufactured (FPGA, then a chip; Exact simulates, Fast translates), and "try it".
- **live** The simple view is the default; Expert view is a remembered switch.
  - **1. Choose a program:** the AI-written platform game (unedited `gpt-6-luna` output from `examples/`, with its session provenance and its own annotations), plus reference programs labelled "made by our own tools, not by the AI".
  - **2. The binary:** every instruction in plain English with its bytes (`apps/web/src/plain.ts`).
  - **3. Run it on the chip.**
  - Examples load and run straight away; the explainer's "Watch the AI's game run" uses the fast engine.
  - Expert-only: fixture list, curated tasks, output mode and claims, export/import, hex inspector, F, counters, trace, compare across F.
- **verified** `tests/e2e/simple-e2e.mjs` (desktop and phone); the other suites start in expert view.

## Engines and chip time (PRD 14B)
- **live** Fast engine: ANMA-1 translated to WebAssembly (`packages/runtime/src/fast/`: a hand-rolled Wasm encoder, the translator, and FastMachine).
  - Differential tests (`packages/runtime/test/fast.test.ts`, 35 tests) show exact agreement with the reference engine on every fixture, both model-generated Mario programs, edge cases and 300 random ALU programs. Modeled ticks equal the exact engine's whenever nothing spills.
  - On the generated Mario: 24 ms/frame against 234 ms/frame exact in Node; 26 fps in headless Chromium on the shared host.
- **live** Engine switch (Exact · Fast); chip-time readout (modeled ms/frame and fps at 100 MHz / 1 GHz / 3 GHz, next to the simulator's measured fps); tick rate 20/30/60, paced to the program.
- **live** Settings remembered across visits (`apps/web/src/settings.ts`).
- **live** Effects hashing writes ASCII effect lines into a reusable buffer and hashes in chunks. The byte stream and hash are unchanged (tested), and it is faster for both engines.

## Chip view (PRD 14A)
- **live** `/chip`: a modeled floorplan driven only by executed micro-events (`onEvent` on the finite machine and on ANMR-1), with declared `anma-cost/1` modeled ticks, a logic analyzer, heat mode, step instruction/microstep, trace export, and deep links. The ANMA-1 vs ANMR-1 capstone compare is implemented but hidden (`SHOW_ANMR_COMPARE`).
- **live** Live chip in the machine panel: instruments the panel's own run (`setEventSink` on the running machine), with speeds from full down to 2 instr/s. It has the terminal and framebuffer beside the die, live keys, and full screen with its own controls.
- **verified** Unit tests: attaching the event listener never changes counters; the event timeline is gap-free and sums to `modeledTicks`; the replayed view state equals the engine state after every instruction (F = 1/4/8/64 and ANMR-1).
- **verified** Browser checks (`tests/e2e/chip-e2e.mjs`, Chromium against staging): step and play advance; the capstone finishes in heat mode; the compare stays hidden; the live chip lights for slowed and full-speed runs, and pong plays in full screen with the framebuffer beside the die; no packets under reduced motion; no horizontal scroll at 390 px; no page errors.
