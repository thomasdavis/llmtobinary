# llmtobinary community OS: product requirements and goal

Status: draft for the owner to set as a goal. Date: 2026-11-07. Revision 3 (website, community and live generation).
Extends `PRD.md` v3.2. Where the two conflict, section 3 of this file says which wins.
Background research: `/home/ajax/reports/LLM machine code to operating system.md`.

## 1. Goal

Turn llmtobinary.com into a community workshop for model-written machine code. People sign in with GitHub, generate programs, and every generation lands in a shared registry that anyone can browse, run, remix and build on. The community then uses that registry to assemble a minimal operating system, and anyone can boot it in their browser. While it runs, a signed-in user can ask for a new program from the shell, and the program arrives on the running system's disk and runs without a reboot.

**The goal is complete when all of these are true:**

1. `node scripts/goal-check.mjs` exits 0, and every acceptance item in section 8 reports `pass` with an evidence file.
2. On https://llmtobinary.com, an anonymous visitor can press **Boot** and get the OS running from a disk image. They can run a program stored on disk, see the shell survive that program trapping, and keep a file across a reboot (A6.1, A6.6).
3. A signed-in user can do the whole loop from the website with no command line: pick an open OS slot, generate a package, see it verified, and see it used in an OS build (A6.7).
4. Every record in the OS image traces to a signed model generation. None came from the fixture builder, a human, or the implementing agent (A6.3).
5. On production, a signed-in user can type a request into the running OS and run the resulting model-written program in that same session, with no reboot (A7.1, A7.6).
6. `docs/OS-STATUS.md` reports the real results of Gates A, B and C, including failures and raw denominators.

Stopping at a gate failure and reporting it (section 7) is a valid outcome. Reaching the demo by weakening a rule in section 4 is not.

**This goal covers phases 0 to 7.** Section 9 lists follow-on work that does not count toward completion.

## 2. Why this is the plan

- No published work shows an LLM writing an OS, or anything close, directly in machine code. The largest model-written program in this repo is 253 records. A minimal OS is estimated at 25,000 to 50,000 records.
- So the unit of generation has to be a small checked package, not the whole binary.
- ANMA-1 has no linking. `CALL` stays inside one file, there are no indirect calls, and a program cannot load another program.
- The main unknown is whether separately generated byte modules can hold a shared interface. Nobody has tested it. Gate B tests it before any kernel work starts.
- Library reuse only helps when something outside the generator controls admission. Open contribution therefore needs a stricter gate, not a looser one.

**What a community changes:**

- It helps with parallel attempts on many components, independent test and spec authors, and people hunting for bugs. Independent authors matter most: a model that writes both code and spec can share one mistake across them.
- It does not fix cross-module reliability, which Gate B measures. Stars and popularity are not evidence of correctness.
- The community site is worth shipping even if the OS stalls, so it comes first.

## 4. Rules for the implementing agent

**Authorship**

- Never write, patch or assemble bytes for any package that ships in an OS build. That includes using a script, the fixture builder or a hand-edited hex file.
- If the model cannot produce a component, record the failure and follow section 7. Do not fill the gap yourself.
- You may write the site, VM, validator, linker, verifier, tests, task specs and interface definitions. Those are the trusted or test side, not the OS.
- Fixtures may test the linker and VM. They must never appear in an OS build.

**Honest evidence**

- Write task specs, interfaces and tests before generating the bytes they judge.
- Do not weaken, delete, skip or special-case a test to get a pass. A test can change only if it is wrong, and the reason goes in `docs/OS-STATUS.md`.
- Do not count `passed-unverified` as `passed`.
- Record every attempt, including failures. Do not rerun until a gate passes without reporting the total number of runs.
- Do not seed fake users, stars, comments or activity on production. The site must show real activity only.

**Repository and deployment**

- Work on the branch `anma-os`. Commit and push to it freely.
- You may merge to `main` when `pnpm run ci` passes (plain `pnpm ci` is a clean install and runs no tests). That deploys staging.
- Do not create `v*` tags, because that deploys production. Production releases are owner actions (section 10).
- Do not run production migrations, change production secrets, or write to production R2 by hand.
- Never print secrets, including anything in `~/.config/llmtobinary/`.
- When a phase needs a production release, prepare it, ask the owner, and carry on with later work on staging in the meantime.

**Money**

- Bulk agent-run work follows the box's spend rule: flat or free lanes, never per-token ones. `PER_TOKEN_USD_BUDGET = 0`, and only the owner can change that line.
- The public site keeps its existing OpenAI generation under the caps the owner already set: $4 per session and $20 per day on production, $0.50 and $1 on staging. Do not raise a cap.
- Staging E2E tests use the fake model unless a test needs a live run, and live runs stay within staging caps.
- OpenRouter and Cerebras pay-as-you-go are never allowed.
- Personal flat subscriptions must not serve public traffic.
- A research lane qualifies only if the model is restricted to the two tools. Coding agents such as Codex qualify only if shell and file tools are provably off, because otherwise the agent could write an assembler.
- Check current lane status first, because the figures in the `spend-lanes` skill may be old.

**The box**

- It is shared and often loaded. Run builds and tests with `nice`.
- `/` is 96% full and `/tmp` is near its quota, so keep bulk output under `/mnt/donto-data`.
- `node_modules` is not installed. Run `pnpm install` first.
- `pnpm test:worker` can time out at startup under load. Record that as an infrastructure failure and rerun it; do not mark it passed.
- The verifier is a background worker, so it must follow the `resource-isolation` skill: CPU and IO deprioritized and memory-capped.

## 6. Design decisions

Change one of these only by writing a short decision note in `docs/OS-STATUS.md` with the reason.

### 6.1 Accounts

The site has no accounts, cookies or database today. Add a GitHub OAuth App, one each for staging and production, and a D1 database.

- Request no scopes, so only public profile data is read. Never request email or repository access.
- Use the authorization code flow with a `state` value bound to a short-lived cookie.
- Discard the GitHub access token straight after reading the profile. Do not store it.
- Identify users by GitHub numeric ID, because logins can change. Keep the login and display name as refreshable metadata.
- Keep sessions in D1, with a `__Host-` cookie that is `HttpOnly`, `Secure` and `SameSite=Lax`. `Lax` is needed because the callback is a cross-site navigation. Allow sign-out and session revocation.
- Keep the existing origin checks on every state-changing route.
- Use a full-page redirect, not a pop-up, because `Cross-Origin-Opener-Policy: same-origin` cuts the link to a pop-up.
- Avatars are blocked by both the `default-src 'self'` CSP and `Cross-Origin-Embedder-Policy: require-corp`. Serve them through a same-origin, cached, size-limited route restricted to GitHub avatar URLs, and fall back to initials. Do not weaken COEP, because the z3 verifier needs cross-origin isolation.
- OAuth runs on the canonical host only.
- Account deletion removes the profile, sessions, stars and comments. Published packages remain and show "deleted user".
- E2E tests use a fake OAuth provider that is enabled only when `ENVIRONMENT` is `test`, following the existing `TEST_FAKE_MODEL` pattern. A test must prove it cannot be enabled on staging or production.

**Roles:** visitor, member (signed in), curator (invited by the owner), owner. Curators accept task specs and tests, and handle reports.

**Quotas (defaults):** a member gets $1 of generation per day, inside the site-wide cap. Show remaining quota in the UI. When the daily cap is used up, say so clearly and let people keep browsing and running. GitHub accounts under 30 days old get a lower quota, to limit sock-puppet accounts.

### 6.2 Licence

The repo has no licence file, so "usable by anyone" has no legal basis yet.

- Default for new generations: **CC0-1.0** for generated bytes, annotations and rendered docs, accepted at sign-in. Licence text is an owner decision (section 10).
- Prompts are published under the same terms, and the sign-in page says so.
- Existing gallery entries show `licence: none stated`. They can be browsed, run and remixed as prompts, but cannot enter an OS build until the owner decides how to handle them.

### 6.3 Versioning

- ANMA-1 and its spec hash do not change. All existing fixtures and gallery entries keep working.
- ANMA-2 is wire version 2, and new capabilities are feature bits. The decoder accepts both versions.
- The Exact engine and reference interpreter must support ANMA-2. The Fast engine may refuse ANMA-2 with a clear message. The chip view only has to not break.

### 6.4 Identity and registry

| Layer | Contents | Storage | Rule |
|---|---|---|---|
| Objects | Blobs at `sha256:<hex>`, plus Interface, Task, Composition and Generation records | R2, public read through the Worker | Write-once, except takedowns (section 6.9) |
| Attestations | in-toto statements in DSSE envelopes, signed with Ed25519: provenance, validation, test, proof, rerun, counterexample, retraction | R2 | Immutable, attached by `subject` |
| Log | Append-only hash chain of publish, attest, bind-name, retract and takedown events | Durable Object plus R2 snapshots | No rewriting; publicly downloadable |
| Views | Search, evidence class, used-by counts | D1 | Rebuildable from the layers above |
| Social data | Users, stars, comments, reports | D1 | Mutable; never affects evidence |
| Lock file | Root, spec and engine digests, one hash per slot, policy hash | Object | The only thing execution trusts |

- Identity is the output hash. A prompt is a request, not a recipe.
- Attribution is the signed-in user recorded by the broker, plus the model and lane. Anyone generating the same bytes creates a new attestation, not a new object.
- Dependencies are exact hash pins. Do not use semver ranges.
- An unknown name fails closed.
- Semantic hashes are derived claims, never primary IDs.
- The server records generations from its own record of the model's tool calls, never from the browser.
- Byte uploads are allowed only as `imported`. They are shown as such and can never enter an OS build.

### 6.5 Verifier

Visitors' browsers cannot establish evidence. Tests running in a browser expose holdouts, and anything a browser reports can be forged.

- `tools/verifier` runs on the box as a capped systemd service and pulls jobs from a queue. It runs guest bytes in the Node VM with fuel limits, outside Cloudflare.
- It holds its own signing key and the private holdout tests. Holdouts are never in the repo, R2 public paths, or the browser.
- Only its signed results raise a package above E2. Browser runs are shown as `client-reported` and never raise a class.
- The site must keep working when the verifier is down. Jobs wait, and the UI shows them as pending.
- A rerun on a different machine with a different key provides E4. The default is a scheduled GitHub Actions job over public test vectors.

### 6.6 Evidence classes

| Class | Meaning | Who can use it |
|---|---|---|
| E0 Archived | Bytes exist, possibly invalid | Anyone can view it and remix its prompt |
| E1 Valid | Validates under a named spec | Anyone can run it |
| E2 Self-consistent | Holds its own claims, or the oracle is model-owned | Anyone can pin it, with a visible warning; never in an OS build |
| E3 Task-tested | The verifier passed it on curator-accepted visible and holdout tests | Automatic selection; **minimum for an OS build** |
| E4 Re-verified | A second verifier reran it bit for bit | Preferred |
| E5 Proved | T3 against a task-owned contract, passing the adequacy checks | Preferred for the trusted core |

So every generation is usable by anyone, and only the OS has a hard admission rule.

- Keep `outcome` separate. The gallery's merged `program = "passed"` field must not carry into the registry.
- Show the evidence class as a label, never as a blended score.
- Stars, comments, usage counts and reputation never raise a class.
- Adequacy checks for E5: the precondition is satisfiable, the postcondition does not hold regardless of the program, all test I/O is accepted, and mutants are rejected.

### 6.7 Linking

- Add IMPORT and EXPORT sections with a symbol, canonical type hash and optional contract hash.
- Imports get ordinary function IDs, so `CALL` keeps its in-file rule and an unlinked module is still checkable.
- The linker resolves symbols, renumbers IDs and emits one file with no imports. **The normal validator then runs on the output.** A linker bug can make a wrong program, but not an unsafe one.
- Dependency hashes live in an external link map, not in the bytes.
- Version 0 forbids cycles and function pointers.
- `HOST` operations become explicit imports, and the linker prints an authority manifest.
- An existing whole program's entry function counts as an implicit export, and its `HOST` calls as implicit imports, so old generations can be called as libraries.
- Each linked edge gets a result: contract hashes equal, z3 implication proved, or runtime-monitored. The program's claim is reported per edge.
- Handles crossing a module boundary carry `own` or `borrow` markers.
- People link in the browser. When a composition is published, the Worker re-links and re-validates it statically, so a forged image cannot be published. This executes no guest code.
- Linked images carry a `linked` label. Say plainly that the linker renumbered IDs but wrote no instruction records.
- Selection runs in the harness, not the model: filter by interface and capabilities, search package cards, then pass at most three candidates into the prompt. A user may pin dependencies by hand. The model still has only its two tools.

### 6.8 Documentation

- The annotation sidecar is the source of truth, and docs are rendered from it.
- Every sentence is tagged: checked, held on N runs, proved, or model's word only.
- Every example runs as a doctest, so a stale doc fails the check.
- Contracts are written from the task before the bytes exist.
- Package cards stay short and structured.
- Selection reads structured fields only. Prompts, comments and model-written prose are an injection surface and never reach a model as instructions. Comments never enter a model's context.

### 6.9 Community features

| Feature | What it does |
|---|---|
| Sign in with GitHub | Attribution, quotas, stars, comments |
| Profile page | A person's generations, packages, accepted tests and counterexamples |
| Registry | Search and filter every generation by interface, capability, evidence class and author |
| Package page | Rendered docs, evidence, attestations, dependencies, used-by, run button, permalink |
| Remix | Start a new generation from a prompt, with lineage shown |
| Compose | Pick packages, link in the browser, run, publish as a named composition |
| Stars and activity feed | Discovery only |
| Comments | Plain text, rate-limited, escaped, reportable |
| OS board | The map of OS slots, with status and open work |
| Break this package | Submit an input that violates a package's accepted contract |
| Builds | Named OS lock files; anyone can boot one, fork it and swap components |

**OS board.** A slot is an interface plus a task spec plus tests, for example `fs.directory`. Anyone can pick an open slot and press **Generate**, with the slot's spec and dependencies already filled in. Several candidates can pass the same slot.

**Choosing the winner.** A slot's default candidate is chosen by rule, not popularity: highest evidence class, then fewest records, then earliest. Anyone can publish a build that makes a different choice.

**Break this package.** The verifier reruns the submitted input against the reference oracle, so the claim needs no trust. If it holds, the package is demoted, dependents are demoted automatically, the contributor is credited, and the input joins the test suite. This turns bug-hunting into a social activity while staying deterministic.

**Contributing tests.** Members can propose tests and specs. Curators accept them, and only accepted ones count as task-owned. A package's author cannot accept tests for their own package.

**Moderation.** Reports go to a curator queue. A *retraction* is an evidence event, and the bytes stay available but cannot be selected. A *takedown* is for abuse or legal requests: the blob and text are removed and a tombstone stays in the log. Lock files pinning it fail closed with an explanation. Extend the existing `gallery-hidden` behaviour rather than replacing it. Terminal output and framebuffers can show anything a prompt asks for, so the report button must appear on package and run pages.

The site keeps its current look and its Simple and Expert views. New pages must work on phones.

### 6.10 OS interface

The host stays a dumb device. `fs.open` on the host would make the VM the OS, so the filesystem, shell and scheduler are all guest bytes.

| Capability | Default operations |
|---|---|
| Text I/O | `input.next_key() -> u64` (full key codes, recorded for replay); `terminal.print_bytes(handle<u8>, offset, length)` |
| Block storage | `block.count()`, `block.read(sector, handle<u8>)`, `block.write(sector, handle<u8>)`, `block.flush()`; 512-byte sectors |
| Program load | `module.load(handle<u8>, length) -> module`: validates the bytes and returns an opaque handle; code is immutable afterwards |
| Tasks | `task.spawn(module, mailbox, fuel, heapQuota) -> task`; `task.resume(task) -> status`; `task.yield(code)` |

- `status` is one of exited, yielded, trapped, or out of fuel.
- A trap ends the task, not the run. Its arena is released when it exits.
- System calls are cooperative: a task writes a request into its `handle<u8>` mailbox and yields, and the kernel services it and resumes the task. This avoids indirect calls and import binding at load time.
- Fuel limits are the preemption mechanism, which keeps replay deterministic. This is a proposal with no kernel precedent, so test it directly.
- Do not add interrupts, privilege levels or an MMU. Isolation comes from unforgeable handles and bytes validated at load.
- Disk images live in the visitor's IndexedDB. A build ships a starter image identified by hash, and that hash is part of run identity. Key input is recorded, so a run replays exactly.
- Registry programs can be copied onto the disk from the OS page, so community programs run on the community OS.

Kernel design rules, following Hyperkernel: fixed tables, loop-free handlers where possible, caller-chosen IDs, run to completion, and complex work kept out of the kernel.

### 6.11 Live generation

A running OS can request a new program. The model runs on the server as it does today, so the guest only hands over a prompt and later receives bytes.

| Operation | Purpose |
|---|---|
| `gen.request(handle<u8>, length) -> job` | Submit a prompt from guest memory |
| `gen.poll(job) -> status` | Returns pending, ready or failed, without blocking |
| `gen.read(job, handle<u8>) -> length` | Copy the finished bytes into guest memory |

The flow is: the user types `gen <prompt>`, the shell keeps responding while the existing generation loop runs, and the shell saves the bytes to disk. `module.load` validates them, and the user runs them as a normal task.

- **Speed:** "real time" means seconds to minutes, not instant. The best recorded small run took 16 seconds, and long sessions have run past 260 seconds. Show live progress and never block the shell. Measure latency and report it; do not promise a figure.
- **Reuse first:** before generating, the shell may search the registry and offer an existing program, which is instant and free.
- **OS interface:** the prompt includes a versioned card describing the OS's system calls, so generated programs target this OS. The card comes from the spec, not from model prose.
- **Evidence:** a live program arrives as E1 or E2 and runs as an ordinary sandboxed task. It is not part of the OS build, so A6.3 and A6.4 still hold. It enters the registry like any other generation, and the verifier can raise its class later.
- **Permission:** only the kernel holds the `gen` capability, and user programs never get it.
- **Spending:** builds are community-made, so a forked kernel could try to spend a visitor's quota. Each request must be confirmed in browser UI outside the guest, showing the exact prompt and remaining quota. Allowing requests for the rest of a session is an explicit choice. Anonymous visitors see a prompt to sign in.
- **Starts stopped:** a new program never starts by itself (`PRD.md` §14). The user runs it with a keypress.
- **Replay:** delivered bytes and job status changes are recorded events, like key input. Replay feeds the recording and never calls the model.
- **Failure:** a failed generation, spent quota or lost connection gives the shell a status and an error message. The OS keeps running.

## 7. Gates and stop rules

Thresholds are proposals. Do not change one after seeing the results it judges. Gates are controlled experiments run by the agent through the research CLI, not community activity.

**Gate A: lane and package size (end of phase 0).** Run 20 independent sessions per size bucket (64, 128, 256 and 512 records) on a qualifying lane, under the `PRD.md` §18.6 protocol.
- Pass: at least one lane reaches 16 of 20 final task success in the 128-record bucket.
- The largest bucket at 16 of 20 or better sets the package size limit.
- Fail: phase 1 continues, but ask the owner before phase 2. They may approve a per-token budget or choose another lane.

**Gate B: shared interface (end of phase 2). This is the decisive test.** Run 20 pairs. Each pair is two independent sessions, using different lanes if two qualify. They write modules against one interface with no contact, and the modules are then linked.
- Pass: 16 of 20 pairs link, re-validate and pass the reference tests with no repair after linking.
- Partial, 8 to 15: improve diagnostics or interface cards and rerun. Allow at most three rounds, and report every round.
- Fail, below 8 after those rounds: **stop the OS work.** Write up the result. Phases 3 to 6 do not start, and the community site stays live. That result is worth publishing.

**Gate C: does reuse compound (end of phase 3).** Compare library on and library off at matched budget on depth 2 and depth 3 tasks, 20 sessions per arm, logging real call edges.
- Report cost-to-pass and the count of real reuse edges.
- This gate does not block phase 4, because the OS can use a curated curriculum. If reuse shows no benefit, say so plainly in `docs/OS-STATUS.md`.

**Stop and ask the owner when:**

- Any gate says to stop or ask.
- A qualifying lane runs out of quota for more than 7 days.
- An OS slot fails 40 sessions across two different task decompositions.
- A rule in section 4 would have to change.
- A step needs an action listed in section 10.
- Abuse, a security issue or a legal request appears on production.

Do not stop for ordinary implementation problems. Fix those and continue.

## 9. Follow-on work, not part of this goal

- **Isolation:** scheduler, copying channels, capability kinds, quotas, drivers as services.
- **Self-hosting:** on-OS package manager, with the assembler and linker in model-written bytes.
- **Verified core:** heap-aware T3, then proofs over the finite kernel interface, with specs from a separate author.
- **Community extras:** direct messages, teams, leaderboards, notifications and bring-your-own API key.
- A compiler branch where a model writes a small compiler in ANMA bytes. Any such branch must be labelled, because it gives up the literal-bytes claim above that layer.

## 11. What the result may claim

If the goal is met, this statement is true:

> Models wrote every instruction record of this operating system as literal bytes, in small packages requested by a community, working against a checker that explained their mistakes but never wrote bytes for them. A linker that wrote no instruction records joined the packages. The OS runs as a guest on a trusted TypeScript virtual machine in your browser. It loads programs from disk and survives their failure. Every package in the OS passed independently held tests, and those results can be rerun bit for bit. While it runs, a model can write a new program on request, and that program runs inside the OS without a reboot.

Do not claim that:

- it runs on hardware or a native chip;
- it is formally verified, unless a named component is actually E5, and then only that component;
- generation is reproducible;
- no human designed the system. People and agents designed the ISA, the interfaces, the tests and the decomposition;
- the VM is verified. It is a trusted base, as large and as important as a kernel, and proofs here say nothing about it;
- star counts or popularity say anything about correctness;
- live-generated programs have the same evidence as the OS packages. They do not until the verifier says so;
- generation is instant.

## 12. Non-goals

Real hardware, a POSIX layer, guest networking, multi-user security inside the OS, multi-core, a graphical desktop, performance claims, the Fast engine for ANMA-2, login providers other than GitHub, payments, and native mobile apps.
